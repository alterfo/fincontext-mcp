# FinContext MCP — open-core, self-hosted финансовый MCP-сервер для РФ SMB

## Context

Соло-разработчик (JS) хочет монетизируемый pet-проект на serverless (Yandex Cloud Functions + YDB). Путь решений (все зафиксированы через уточняющие вопросы):
1. Разведка рынка → **отказ от селлерских инструментов WB/Ozon**: нишу «AI-автоответы на отзывы» в феврале 2026 нативно съел сам Wildberries + рой бесплатных сервисов → соло там рва нет. Урок: на хайповых рынках против соло стоят и площадка, и венчур, и бесплатные тулы.
2. Пивот **«оттолкнуться от преимущества»**. Преимущество: AI-агенты/MCP + JS + DevOps + кросс-доменный опыт (FinTech/GovTech/EdTech/PropTech/HRTech) + доступ к dev-сообществу.
3. Якорь-вертикаль → **FinTech**.
4. Ключевое ограничение: резидент РФ **без доступа к Stripe/PayPal** → деньги через YooKassa (РФ).
5. Возражение о доверии (никто не отдаст соло токены к банкам) → решено **архитектурно**: модель **self-hosted / open-core** — токены живут у клиента, к разработчику не уходят.

## Итог разведки (обоснование ниши)

- **Боль системная:** кассовые разрывы — массовая проблема 2026, ~27% компаний/ИП столкнулись впервые. Деньги размазаны по нескольким банкам + учётным системам, ручная сверка выписок болит.
- **MCP-в-финансах — топ-кейс мира 2026:** официальные MCP-серверы у QuickBooks (Intuit×Anthropic), Xero, Zoho Books; Goldman посадил Claude на сверку. Направление подтверждено.
- **Зазор:** СберБизнес MCP — единственный корпоративный MCP в РФ, но это стена одного вендора (только клиенты Сбера, только его операции). **Нейтрального кросс-банковского + учётного MCP нет** — ни у Сбера, ни у западных (не знают 1С/Контур/Точку).
- **Кубики для соло есть:** Точка Банк — бесплатный public API; МойСклад — открытый API + импорт выписок из Сбера/Альфы/Точки/Модуля/Т-банка; интеграции 1С/Контур.
- **Ров для соло:** нейтральность + покрытие 1С/Контур/Точки + FinTech-глубина (сверка, ИП/УСН/НДС, банковские причуды) + дистрибуция через dev-сообщество. Платформа не съест — кросс-вендорную агрегацию ни один вендор не строит.

## Продукт и модель (open-core, self-hosted)

**FinContext MCP** — нейтральный MCP-сервер, дающий AI-агенту сводный финансовый контекст SMB по всем банкам и учётной системе. Tools:
- `get_cash_position` — реальный кэш по всем счетам;
- `check_payment` — прошёл платёж или висит;
- `cashgap_forecast` — прогноз кассового разрыва;
- `reconcile` — сверка выписка↔учёт (частичные оплаты, отсутствующие назначения, разные форматы).

**Модель доверия/монетизации:**
- **Клиент разворачивает MCP у себя** — токены банков/учёта лежат в *его* Lockbox/env, к разработчику не уходят. Доступ к банкам — **только read-only scope**.
- **Open-core:** открытое ядро (протокол MCP + базовые коннекторы Точка/МойСклад) = аудируемость → доверие через прозрачность, а не бренд. **Закрыто/по лицензии:** движок сверки (`reconcile`), прогноз разрыва, premium-коннекторы (1С/Контур/др. банки), алерты.
- **Целевой покупатель — билдеры/интеграторы** финансовых агентов (аудитория пользователя; взрывной наём Сбер/Яндекс/МТС/X5). Они self-host'ят коннектор → разработчик не видит данные в принципе.
- **Заработок (YooKassa, РФ):** Pro-лицензия (ключ разблокирует premium-модули) + платная поддержка/внедрение + опциональный managed-хостинг позже, для тех, кто уже доверяет.

## Роль Yandex FaaS

- **Основной артефакт деплоя — Terraform-модуль**, который разворачивает MCP в **облако клиента (его Yandex Cloud): Functions + API Gateway + YDB + Lockbox**. Serverless = дёшево, без ops — сильный аргумент для self-host.
- **Твой демо-инстанс** на собственном FaaS — для маркетинга/песочницы (на демо-данных, без чужих токенов). Так FaaS-навык прокачивается на обеих сторонах.

## Архитектура

- `functions/mcp/index.js` — HTTP-функция за API Gateway, MCP по streamable-HTTP (JSON-RPC): `initialize`, `tools/list`, вызовы tools.
- `functions/sync/index.js` — timer-триггер: тянет свежие выписки/оплаты в кеш (YDB), пересчитывает кэш-позицию/прогноз.
- `src/mcp.js` — регистрация tools и роутинг JSON-RPC.
- `src/reconcile.js` — **доменное ядро** (сверка/кэш-позиция/прогноз) — главный носитель рва; premium.
- `src/connectors/{tochka,moysklad,kontur,1c}.js` — адаптеры + нормализация выписок в единую модель (tochka/moysklad — open; kontur/1c — premium).
- `src/ydb.js`, `src/lockbox.js` — инфраструктура (читают токены из Lockbox *клиента*).
- `src/license.js` — проверка Pro-ключа (офлайн-валидация подписи, без телеметрии — важно для доверия).
- `infra/` — Terraform (провайдер `yandex`): функции, API Gateway (OpenAPI), timer-триггер, YDB, Lockbox, сервис-аккаунт с минимальными правами. Это и есть поставляемый клиенту деплой.
- `README`/`docs/` — прозрачная модель безопасности (что хранится, что НЕ уходит наружу), инструкция подключения MCP-клиента.

## Как разрабатывать и тестировать (свой бизнес НЕ нужен)

Слоёный цикл разработки; для старта не требуется ни SMB, ни реальные деньги, ни чужие токены:

1. **Доменное ядро на синтетике (0 доступов).** `src/reconcile.js` и прогноз — чистые функции. Генеришь синтетические выписки+проводки с заранее известными расхождениями → Jest. Это большая часть ценности/рва, тестируется полностью локально.
2. **Точка — песочница «из коробки» (0 регистраций).** URL → `https://enter.tochka.com/sandbox/v2`, `Authorization: Bearer sandbox.jwt.token` (все права, тестовые данные, прод не трогается). Коннектор Точки пишешь/тестируешь без реального счёта.
3. **МойСклад — бесплатный тестовый аккаунт.** JSON API бесплатен на всех тарифах; отдельной песочницы нет — регистрируешь бесплатный тестовый аккаунт и сам наполняешь тестовыми товарами/оплатами.
4. **MCP Inspector — локальный драйв сервера.** `npx @modelcontextprotocol/inspector` (web/CLI/TUI, streamable-HTTP) → вызываешь `tools/list`, `get_cash_position`, `reconcile` без деплоя; CLI-режим = автотесты в CI.
5. **FaaS-интеграция.** Логика в `src/` (эмулятора YC нет) → деплой dev-версии функции → вызов через API Gateway → Cloud Logging. Terraform-модуль проверяешь развёртыванием в чистый YC-каталог.
6. **Реальные данные — потом и опционально.** Для живого e2e открой самозанятость/ИП (нужно всё равно для YooKassa) + счёт в Точке + бесплатный МойСклад → станешь **своим первым клиентом** (dogfooding), затем design-partner из dev-сообщества.

Ключ: пункты 1–4 не требуют ни бизнеса, ни реальных денег, ни чужих токенов.

4. **МойСклад** (бесплатный тестовый аккаунт) → включить `reconcile` (ядро ценности; premium).

6. YooKassa: продажа Pro-ключа (это продажа софта/лицензии, не сервиса-хранилища — юридически проще).

## Проверка (end-to-end)

- Юнит-тесты `src/reconcile.js` и коннекторов (Jest) локально — эмулятора YC нет, доменная логика отделена от handler'ов.
- E2E MCP: подключить локальный MCP-клиент (Claude Desktop / MCP-инспектор) к своему демо-инстансу → `get_cash_position` и `reconcile` на демо-данных → сверить с ручным расчётом.
- Проверка Terraform-деплоя: развернуть модуль в чистый YC-каталог, убедиться, что MCP поднимается и читает токены из Lockbox этого каталога.
- Проверка лицензии: без Pro-ключа premium-tools недоступны; с валидным ключом — открываются (офлайн, без обращения к твоим серверам).
- Проверка sync/дедупа: повторный проход не задваивает транзакции.
- Логи в Cloud Logging (`yc logging read`).

## Риски / открытые вопросы

- **Монетизация open-core:** держать премиум-ценность (движок сверки, прогноз, 1С/Контур, алерты) достаточно весомой, чтобы за Pro платили; открытое ядро — «на попробовать» и для доверия. Доп. канал — платное внедрение/поддержка.
- **«Платят ли за open source»:** да — за premium-модули, поддержку и managed-хостинг; плюс бизнес платит за деплой+сопровождение. MRR умеренный, но реальный — ок для pet-проекта.
- **Хрупкость API** банков/учёта — изолировать в `connectors/*`, версионировать, мониторить.
- **Юр. аспект приёма оплаты:** оформить самозанятость/ИП для YooKassa; продажа лицензии проще, чем обработка чужих финданных (её ты избегаешь by design).
- **Стартовое покрытие:** только Точка + МойСклад; расширять по спросу, не пытаться покрыть все банки сразу.
- **Лицензионная модель open-core:** выбрать лицензию (напр. открытое ядро под пермиссивной, premium-модули — проприетарные/по коммерческой лицензии). → решение в разделе «Выбор лицензии».

## Модель данных (нормализация)

Весь ров держится на **единой модели проводки**: разные источники (банки/учёт) приводятся к одному виду, дальше `reconcile`/прогноз работают источник-независимо. Всё храним в YDB *клиента*.

### `Transaction` — нормализованная операция (общая для банка и учёта)

| Поле | Тип | Смысл |
|---|---|---|
| `id` | string | стабильный ID = `hash(source, source_account_id, native_id)` |
| `source` | enum | `tochka` \| `moysklad` \| `kontur` \| `1c` |
| `kind` | enum | `bank` \| `ledger` — банковская операция или проводка учёта |
| `account_id` | string | счёт/касса внутри источника |
| `direction` | enum | `in` \| `out` |
| `amount` | int64 | **в копейках** (minor units), без плавающей точки |
| `currency` | string | ISO-4217, старт — только `RUB` |
| `booked_at` | date | дата проведения |
| `value_date` | date? | дата валютирования (у банков ≠ booked_at) |
| `status` | enum | `posted` \| `pending` \| `hold` |
| `counterparty` | object? | `{ name, inn, kpp?, account?, bic? }` |
| `purpose` | string? | назначение платежа (сырой текст) |
| `doc_number` | string? | номер платёжного документа |
| `uin` | string? | УИН (налоги/госплатежи) |
| `vat_amount` | int64? | выделенный НДС в копейках (важно для УСН/НДС-сверки) |
| `category` | string? | категория (заполняется правилами/позже) |
| `dedup_key` | string | ключ идемпотентности sync (см. дедуп) |
| `raw` | json | исходный объект источника — для аудита и разбора причуд API |

Инвариант: `amount` — всегда положительный int64 в копейках; знак несёт `direction`. Никаких float — деньги только целыми.

### `Statement` — выписка (контейнер банковских операций за период)

`{ account_id, source, period_from, period_to, opening_balance, closing_balance, fetched_at, line_ids[] }`. Служит для проверки целостности: `opening + Σ(in) − Σ(out) == closing` (контроль полноты загрузки).

### `CashPosition` (материализованное представление, пересчитывается sync-триггером)

`{ as_of, by_account: [{account_id, source, balance, currency, updated_at}], totals: {currency: balance} }`.

### Таблицы YDB (у клиента)

- `accounts` — реестр счетов/касс с источником и валютой.
- `transactions` — нормализованные операции (PK: `id`; вторичный индекс по `account_id + booked_at`).
- `statements` — метаданные выписок для контроля полноты.
- `reconcile_runs` — результаты сверок (для истории/идемпотентности).
- `sync_state` — курсоры инкрементальной подкачки по каждому источнику (last cursor / last booked_at).
- `positions` — материализованная кэш-позиция и данные для прогноза.

### Дедуп / идемпотентность sync

`dedup_key = hash(source, account_id, native_id)` при наличии стабильного ID источника; иначе — `hash(source, account_id, booked_at, amount, direction, doc_number|purpose)`. `PUT` по `id` — повторный проход перезаписывает ту же строку, не задваивает. Курсор в `sync_state` двигаем только после успешной записи батча.

## Контракты MCP-tools (input/output)

JSON-RPC поверх streamable-HTTP. Ниже — контракты; `tools/list` отдаёт JSON Schema для `inputSchema`. Premium-tools (`reconcile`, `cashgap_forecast`, алерты) в `tools/list` **скрыты** без валидного Pro-ключа.

### `get_cash_position` (open)
- **in:** `{ as_of?: date, accounts?: string[], currency?: string="RUB" }`
- **out:** `{ as_of, total: {amount, currency}, by_account: [{account_id, bank, amount, currency, updated_at, staleness_sec}], warnings: [] }`
- `staleness_sec` и `warnings` — честность про свежесть кеша (например, «Точка не синкалась 3ч»), критично для доверия к цифре.

### `check_payment` (open)
- **in:** `{ amount?: int64, counterparty_inn?: string, purpose_contains?: string, doc_number?: string, uin?: string, date_from?: date, date_to?: date }`
- **out:** `{ status: "found"|"pending"|"not_found", matches: [{transaction, account_id, confidence}], explanation }`
- Разводит «прошёл» (`posted`) vs «висит» (`pending`/`hold`) — прямой ответ на живой вопрос «деньги пришли?».

### `cashgap_forecast` (premium)
- **in:** `{ horizon_days: int=30, scenario?: "base"|"conservative"="base", include_recurring?: bool=true }`
- **out:** `{ horizon_days, current_position, daily: [{date, projected_balance, inflows, outflows}], gap: {will_occur, first_gap_date?, min_balance, deficit_amount?}, assumptions: [] }`
- `assumptions` явно перечисляет допущения (регулярные платежи, дебиторка) — прогноз без чёрного ящика.

### `reconcile` (premium — ядро ценности)
- **in:** `{ period: {from, to}, bank_source, ledger_source, tolerance?: {amount_minor: int64=0, days: int=0} }`
- **out:**
  - `summary: { matched, matched_amount, unmatched_bank, unmatched_ledger, partial }`
  - `matched: [{ bank_txn_id, ledger_entry_id, amount, match_type: "exact"|"tolerance" }]`
  - `exceptions: [{ type, bank_txn?, ledger_entry?, delta?, suggestion }]`
- Типы исключений (`type`): `missing_in_ledger`, `missing_in_bank`, `amount_mismatch`, `partial_payment` (несколько проводок под один платёж), `duplicate`, `purpose_ambiguous`. `suggestion` — гипотеза сопоставления для человека. Именно качество разбора этих кейсов (частичные оплаты, разные форматы назначения, ИП/НДС-причуды) — то, что не умеет ни один вендорский MCP.

**Общий формат ошибок:** premium-tool без лицензии → JSON-RPC error `{ code, message: "premium: требуется Pro-ключ", data: { upgrade_url } }`.

## Лицензирование Pro-ключа (офлайн, без телеметрии)

Доверие требует, чтобы проверка ключа **не ходила на серверы разработчика**. Механизм — офлайн-подпись:

- **Крипто:** Ed25519. Приватный ключ — только у разработчика (офлайн-генератор ключей). Публичный ключ вшит в `src/license.js` (он в открытом ядре — проверяемо).
- **Формат ключа:** `base64url(payload) + "." + base64url(signature)`.
- **Payload:** `{ sub: customer_id, plan: "pro", modules: ["reconcile","forecast","alerts","connectors:kontur","connectors:1c"], iat, exp?, seats? }`.
- **Проверка (`src/license.js`):** декод payload → верификация подписи публичным ключом → проверка `exp` (если задан) → возврат множества разблокированных `modules`. Никаких сетевых вызовов, никакой телеметрии.
- **Гейтинг:** `tools/list` фильтрует premium-tools по `modules`; вызов premium-tool при отсутствии модуля → error с `upgrade_url`. Premium-коннекторы (`kontur`/`1c`) грузятся только при наличии соответствующего `connectors:*`.
- **Продажа:** YooKassa (оплата) → офлайн-генератор выпускает подписанный ключ клиенту (это продажа лицензии на софт, не хранение чужих финданных — юридически проще).
- **Отзыв:** офлайн-модель не отзывает мгновенно; используем короткий `exp` + перевыпуск при продлении. Компромисс сознательный: приоритет доверию.

6. Что вы или клиент реально готовы селф-хостить? Что было бы барьером к self-host?
7. Кто принимает решение платить за инструмент/лицензию и какой на это бюджет?
8. Что похожее покупали за последний год и сколько заплатили?
9. Что должно быть внутри готового нейтрального MCP, чтобы вы его взяли? Что блокирует прямо сейчас?
10. Кого ещё стоит расспросить по этой теме?

**Порог «валидировано» (иначе — пивот/сужение):** из ~10 разговоров ≥3 имеют одновременно (а) активную, а не гипотетическую боль в агрегации/сверке; (б) бюджет и лицо, принимающее решение; (в) готовность селф-хостить. Плюс приоритезированный список premium-коннекторов из вопроса 3 (что тянуть после Точки/МойСклада).

## Выбор лицензии (open-core)

- **Открытое ядро** (протокол MCP, `functions/mcp`, коннекторы Точка/МойСклад, `src/license.js`, инфра-обвязка) — **Apache-2.0**: пермиссивно + явный патентный грант → максимальное принятие билдерами/интеграторами, дружелюбно к бизнесу. Открытость `license.js` — часть аргумента доверия (проверяемо, что нет телеметрии).
- **Premium-модули** (`src/reconcile.js`, прогноз, алерты, коннекторы `kontur`/`1c`) — **отдельный проприетарный/коммерческий репозиторий или каталог**, поставка по Pro-ключу; не в open-ядре. Как вариант защиты от конкурирующего managed-хостинга — **BSL (Business Source License)** с авто-конверсией в open через N лет.
- **Контрибуции:** на ядро — **DCO** (Signed-off-by), без CLA, чтобы не отпугивать контрибьюторов. Premium внешних контрибуций не принимает → CLA на ядро не нужен.
- **Нейминг/защита:** имя/лого — товарный знак; лицензия ядра разрешает форк кода, но не бренд и не premium.

## Коннекторы: расширение и маркетплейсы (Ozon/WB)

Нейтральность = ров, а ров = **широта источников**. Архитектура pluggable: `src/sync.js` источник-независим, добавление источника = один файл (`pull(period) → {accounts, statements, transactions}`, нормализация в общую модель) + регистрация в `src/connectors/index.js` + токен в Lockbox. Контракт и how-to — в [`docs/CONNECTORS.md`](CONNECTORS.md); шаблон — `src/connectors/_template.js`.

- **Банки** (`kind: bank`) — прямой аналог Точки. Приоритетные premium-кандидаты: **Т-Банк (Бизнес)** (лёгкий токен, SMB/ИП), **Альфа** (тяжелее онбординг, возможен mTLS). Сбер вне скоупа — у него свой одновендорный MCP.
- **Маркетплейсы** (`kind: marketplace`, новый вид) — **Ozon Seller** (`Client-Id`+`Api-Key`) и **Wildberries** (токен по скоупам). Это не банк, а взаиморасчёты продавца: продажи, комиссии, холды, **выплаты**. Ключевая ценность для кассового разрыва: большой лаг между продажей и выплатой площадки → **ожидаемые выплаты кормят `cashgap_forecast` как запланированные притоки**. Это финансовая агрегация, а не переполненная ниша «AI-автоответы на отзывы» — пивоту не противоречит, ров усиливает. Модель уже расширена (`SOURCES += ozon,wb`, `KINDS += marketplace`); коннекторы заявлены как premium (`connectors:ozon/wb`). Ключи самообслуживаемые → онбординг дешевле банковского; порядок реализации — по итогам M0-валидации.
